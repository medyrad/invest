# مشخصات PROGRAMMER-S04-03 — مقدار و تعریف فیلد

مرجع: D29 در docs/stage1/production-decisions.md:82–98، FR-029/030 و بخش T009/T011 پایه. اختیار همین مأموریت؛ S05، فرم‌ساز، محاسبات خدمات، FX، IRR و UI خارج از دامنه‌اند.

## داستان‌ها و پذیرش
### US1 / P1 — مبلغ دقیق
مصرف‌کننده فرم آینده، مبلغ با واحد صریح می‌دهد و همان مقدار دقیق را دریافت/ذخیره می‌کند. ۱٫۵ میلیارد و۱۵۰۰میلیون، هر دو۱۵۰۰۰۰۰۰۰۰TOMAN؛ API فقط رشته اعشاری. عدد فارسی/عربی و گروه‌بندی معتبر پذیرفته، ورودی مبهم/بیش‌دقت رد شود؛ صفر/unknown/not_applicable مستقل.
### US2 / P1 — واحد و مبنای روشن
Quantity و ReturnMetric واحد و نسخه/مبنا دارند. ماه به روز یا سال تبدیل نشود؛ FX و IRR محاسبه نشوند. مقایسه داخلی داده نامعلوم/ناهم‌فیلد/ناهم‌نسخه/ناهم‌مبنا معتبر نیست؛ نتیجه رتبه‌بندی محصول نیست.
### US3 / P1 — تعاریف قابل استفاده
FieldDefinition نسخه‌دار با namespace، معنا، حضور/unknown، حدود، منبع و واحدهای مجاز؛ چند فیلد مشخص مرجع نگاشت شوند. تعریف منتشرشده و داده تاریخی دوباره تفسیر نشوند؛ PostgreSQL رفت‌وبرگشت واقعی داشته باشد.

## نیازمندی‌ها
- FR-001: MoneyValue/Quantity/ReturnMetric و UnitDefinition/FieldDefinition نسخه‌دار؛ نگاشت namespace صریح و immutable.
- FR-002: domestic base=TOMAN؛ source_value/source_unit/version/factor حفظ؛ ارز خارجی با کد/مقدار خودش، هیچ FX. API رشته و Decimal دقیق، نه float.
- FR-003: known با عدد، unknown/not_applicable بدون عدد؛ صفر مستقل؛ input null فقط با status غیرknown، نه حدس از رشته خالی.
- FR-004: ارقام فارسی/عربی/لاتین و ممیز . یا ٫؛ جداکننده , یا ٬ فقط سه‌رقمی و یک سبک. فاصله داخلی، ممیز ویرگول، e، NaN، infinity، bool/number، بیش‌دقت/حدود رد شوند. علامت منفی فقط در نوع بازده مجاز.
- FR-005: ظرفیت فنی عمومی abs≤999999999999999999999999.999999999 و scale≤9؛ پول/مقدار غیرمنفی، شمارش صحیح؛ حدود فیلد می‌تواند تنگ‌تر باشد. این سقف ظرفیت ذخیره است، نه سقف تجاری فرصت. Return درصد نیز در همان ظرفیت فنی، با نوع و دوره و افق و تاریخ Gregorian و اسمی/واقعی و سطح و observation/source صریح؛ known بدون مبنای کامل رد شود. Quantum ورودی واحدهای پول۹ رقم است؛ ضرب دقیق باز هم باید scale≤9 و حد فیلد را رعایت کند؛ هیچ truncate/round نیست.
- FR-006: فقط تبدیل در واحدهای یک بُعدِ تعریف‌شده؛ MONTH/YEAR/DAY پایه مستقل. Quantity مدت برای مقایسه start_basis صریح می‌خواهد؛ داده مرجع فاقد آن با برچسب unspecified می‌ماند و مقایسه نمی‌شود.
- FR-007: نگاشت محدود source→field/unit/meaning؛ minCapital≠budget، monthlyRent≠deposit، minimumMillion فضای fund مستقل؛ نبود مبنای IRR مرجع جعل نشود.
- FR-008: schema ماشین‌خوان، API خواندن تعریف و normalize بدون ذخیره/فرم/مجوز فرصت؛ خطا با message فارسی و code/field روشن. قواعد قبلی و ظاهر ثابت.

## موجودیت‌ها
UnitDefinition، FieldDefinition، MoneyValue، Quantity و ReturnMetric؛ value رکورد مشترک فرم آینده است، فعلاً CRUD عمومی یا وابستگی Opportunity ندارد.

## معیارهای موفقیت
SC-001: آزمون‌های دقیق تبدیل/مرز/parser/JSON و PostgreSQL بدون از دست‌دادن مقدار پاس شوند؛ SQL مستقیم بیش‌دقت را نیز رد کند.
SC-002: unknown و ناسازگاری نسخه/واحد/مبنا نتیجه مقایسه معتبر ندهند؛ مقایسه ارزش‌های هم‌مبنا صحیح باشد.
SC-003: migration forward/backward روی DB آزمون، تعریف/نگاشت نسخه‌دار و شواهد نسخه/گزارش؛ پوشش فیلدهای پنهان آینده و کل T011 ادعا نشود.

## فرض‌ها و مرزها
حضور داده با knownبودن یکی نیست؛ required تعریف به حضور داده اشاره دارد و جای الزامات فرم S05 نیست. D29 سیاست مصوب است؛ تعیین ظرفیت فنی و grammar مهندسی در همین مأموریت مجاز شده. شرط نمایش metadata غیر اجرایی و inactive_effect=exclude است؛ اجرای واقعی شرط‌ها و ارسال فرم در این بسته پذیرفته نمی‌شود. تأیید انسانی/کل S04 باز است.

## اصلاح PROGRAMMER-S04-04 — TEST-S04-03
FR-009: NUL در ref و سایر متن‌های قرارداد پیش از lookup رد شود؛ HTTP400 با envelope، پیام فارسی و مسیر فیلد. حذف NUL یا catch عمومی خطاهای سرور مجاز نیست.
FR-010: قواعد basis فعلی در INSERT/UPDATE مستقیم نیز برقرارند: Money فقط null، Quantity مدت object دقیق start_basis رشته غیرخالیِ canonical تا۲۰۰کاراکتر، سایر Quantity فقط null؛ Return در known مبنای کامل و هم‌نوع با تعریف می‌خواهد، در unknown/not_applicable مبنای null یا کاملِ معتبر. نوع/کلید/enum/نسخه/افق مثبت دقیق/تاریخ معتبر/منبع غیرخالی کنترل شود. SQL NULL و JSON null معادل None در قراردادند؛ برای known Return و تمام وضعیت‌های مدت مجاز نیستند. افق ذخیره‌شده canonical است، مانند خروجی normalize؛ ورود ارقام محلی همچنان در normalize پذیرفته/نرمال می‌شود.
SC-004: همان۶شکست مستقل سبز، مجموعه۱۰۶تایی و مستقل۵۳تایی روی نسخه نهایی یک بار، همراه تست‌های افزودهٔ مثبت/منفی و rollback ایزوله؛ داده ناسازگار موجود مانع migration است، نه مجوز اصلاح/حذف خودکار.
