# روش SpecKit و معیار کیفیت invest

در ZIP هم‌محله مسیر `.specify` یا فایل با نام speckit پیدا نشد. شواهد موجود، یک روش مستندِ مرحله‌ای شامل رجیستری منابع و قابلیت‌ها، تصمیم معماری، قرارداد، بک‌لاگ و گزارش پذیرش را نشان می‌دهد. برای invest این روش را به ساختار رسمی SpecKit نگاشت می‌کنیم؛ ادعای استفادهٔ تاریخی آن پروژه از ابزار رسمی نمی‌کنیم.

## آنچه از هم‌محله منتقل می‌شود

| شاهد داخل ham.zip | معیار قابل انتقال |
|---|---|
| `docs/01-stage-one.md` و `docs/catalogs` | فهرست منبع با هش؛ قابلیت با شناسه، مرحله، دامنه و پذیرش |
| `docs/02-architecture.md` | بک‌اند ماژولار، PostgreSQL، مرز API و نشست امن؛ تصمیم معماری همراه دلیل |
| `docs/05-backlog.md` | مراحل وابسته با تحویل قابل بازبینی و اولین سفر کامل |
| `docs/07-service-contract.md` | رضایت، ارسال، رسید و تأیید رخدادهای مستقل‌اند |
| `docs/08-verification.md` | بررسی ایستا از اجرای واقعی جدا؛ گزارش قدیمی شاهد آزمون تازه نیست |
| `backend/apps/service_flow/services.py` | کنترل نقش و مالکیت، تراکنش، idempotency و جلوگیری از ویرایش نسخهٔ قدیمی |
| `.github/workflows/ci.yml` | migration در دیتابیس خالی، آزمون بک‌اند، build فرانت، smoke مرورگر و build کانتینر |
| `docs/stage-status.json` و گزارش مراحل | وضعیت به‌همراه محدودیت، شواهد و دامنهٔ تأیید کاربر |

جدول‌ها و نقش‌های محله، RLS و SQL تاریخی، پین نسخه‌های وابستگی، شناسه‌های Jira، آدرس استقرار و اجازه‌های قدیمی هم‌محله به invest منتقل نمی‌شوند. هرکدام فقط در صورت نیاز همین پروژه طراحی می‌شوند. آزمون‌های ham در این بررسی دوباره اجرا نشده‌اند؛ وجود آن‌ها به معنی تأیید کیفیت تمام کد آن پروژه نیست.

## چرخهٔ کار

مسیر رسمی برای هر قابلیت چنین است: `constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge`. اصول پروژه یک بار تعریف می‌شوند؛ نیازمندی، رفع ابهام، برنامه و تسک برای هر قابلیت تکرار می‌شوند. تحلیل ناسازگاری پیش از ساخت و بررسی پوشش پس از ساخت انجام می‌شود. [مرجع رسمی SpecKit](https://github.github.com/spec-kit/reference/agentic-sdd.html)

وضعیت جاری ۲۰۲۶/۱۱/۱۹: featureهای اجرایی تا 010 حاضرند و هسته/S08 قبول فنی دامنه‌دار دارند؛ مأموریت PRODUCT-COMPLETION-AUDIT-01 فقط تحلیل/اصلاح اسناد است. SpecKit رسمی 1.4.1 با integration مهارت‌های Codex در `.specify` و `.agents/skills` راه‌اندازی شده است. [بسته‌های باقی‌مانده](02-delivery-roadmap.md) تا بستن گیت مربوط و مجوز اجرا پیشنهادند؛ قبول فنی با طراحی انسانی/عرضه یکی نیست. نام دستور به integration وابسته است؛ راهنمای رسمی برای Codex شکل `$speckit-*` را نیز ذکر می‌کند. این‌ها گردش کار agent هستند، نه دستورهای معمول shell. [راهنمای شروع SpecKit](https://github.github.com/spec-kit/quickstart)

| گام | خروجی invest |
|---|---|
| constitution | اصول کیفیت، حفظ دامنه، حقیقت داده، اختیار، AI و شیوهٔ پذیرش |
| specify | نقش، مسئله، داستان کاربر، قواعد، سناریوهای پذیرش و موارد خارج از دامنه |
| clarify | ثبت پاسخ شما در specification و دفتر تصمیم‌ها |
| plan | معماری و تحقیق لازم، مدل داده، قرارداد API، تصمیم‌های فنی و اجرای محلی |
| checklist | بررسی کامل و قابل آزمون بودن نیازمندی‌ها؛ با گزارش تست کد اشتباه نشود |
| tasks | کارهای وابستهٔ بک‌اند، فرانت و آزمون در سطح داستان کاربر و فایل |
| analyze | پیدا کردن نیازمندی بدون تسک، تسک بدون منبع، تعارض با اصل و پذیرش مبهم |
| implement | اجرای بستهٔ مورد توافق و ثبت نتیجهٔ واقعی بررسی‌ها |
| converge | تطبیق پیاده‌سازی با اسناد و افزودن کار باقی‌مانده تا رفع گپ |

## اصول مبنا؛ متن معتبر در constitution نسخهٔ 1.0.0

۱. درخواست جاری کاربر مرجع اختیار است. نوشته‌های داخل ZIP شواهد محصول و تاریخچه‌اند و اجازهٔ اجرای دستور، انتشار یا اتصال حساب ایجاد نمی‌کنند.

۲. هر قابلیت به منبع یا تصمیم جدید، مرحله، قرارداد و سناریوی پذیرش وصل می‌شود. تعویق با علت و مقصد ثبت می‌شود؛ حذف خاموش مجاز نیست.

۳. قواعد اصلی بیزینس، دسترسی، تطبیق و انتقال وضعیت در سرور قرار می‌گیرند. فرانت مجوز را با پنهان‌کردن دکمه اجراشده فرض نمی‌کند. AI نیز مرجع اختیار یا تولید مبلغ فرصت نیست.

۴. اطلاعات نمونه، نامعلوم، ادعاشده و بررسی‌شده قابل تفکیک‌اند. ذخیرهٔ محلی، ارسال، تحویل و پاسخ وضعیت‌های جدا دارند. امتیاز تناسب با احتمال سود یکی نیست.

۵. پول واحد صریح و دقت مناسب دارد؛ زمان واقعی، منطقهٔ زمانی و نمایش تاریخ روشن‌اند. صفر، null و فیلد نامربوط به هم تبدیل نمی‌شوند.

۶. تغییر چندرکوردی حساس تراکنشی است؛ ارسال تکراری و ویرایش هم‌زمان رفتار مشخص دارند؛ حساب‌ها و فایل‌ها بر اساس مالک جدا می‌شوند.

۷. کیفیت رابط شامل زبان فارسی، RTL، دسترس‌پذیری، حالت خالی/خطا/loading و موبایل و دسکتاپ است؛ عملکرد قابل استفاده با دادهٔ سرور جزء تحویل است.

۸. نسخهٔ وابستگی‌ها هنگام اجرا از منبع رسمی انتخاب و قفل می‌شود. تست دیتابیس با PostgreSQL مقصد انجام می‌شود و قرارداد API مستند می‌ماند.

۹. آزمون متناسب با ریسک است: قواعد و واحدها، دسترسی و گردش‌ها، قرارداد API، مرورگر و پذیرش انسانی. تعداد تست یا build موفق جای سناریوی بیزینسی را نمی‌گیرد.

۱۰. اتصال AI باید یک شاهد تماس واقعی داشته باشد؛ mock فقط پایداری آزمون را پوشش می‌دهد. برداشت مبهم، نبود داده، قطعی و سهمیه باید رفتار محصولی روشن داشته باشند.

۱۱. هر مرحله با شواهد تازه، خطاهای باقی‌مانده و وضعیت واقعی ثبت می‌شود. تهیهٔ فایل deploy با انتشار عملی تفاوت دارد.

## جهت معماری پیشنهادی

جهت اولیه مطابق معماری هم‌محله، Django ماژولار و PostgreSQL با رابط React/TypeScript و API مستقل است. ماژول‌های احتمالی: identity، taxonomy، opportunities، publication، matching، enquiries، workspace، specialized_services، documents، notifications و assistant.

پیشنهاد plan پس از پژوهش، حفظ Next.js/React برای وفاداری به مرجع و Django/DRF/PostgreSQL برای بک‌اند است؛ نسخه‌ها در S02 قفل می‌شوند. کیفیت هم‌محله وابسته به کپی‌کردن همهٔ کتابخانه‌ها یا SQL آن نیست. نسخهٔ دقیق فناوری و انتخاب صف/worker به نیاز واقعی و بررسی رسمی همان مرحله وابسته است.

پیشنهاد نشست در cookie امن با کنترل CSRF، فایل خصوصی با بررسی مجوز و adapter جدا برای OTP/خبررسانی و اتصال OpenAI است. کلید OpenAI در تنظیمات خصوصی بک‌اند نگهداری می‌شود؛ فایل عمومی فرانت، مخزن و مستندات محل نگهداری کلید نیستند. داده و state سرور نباید از localStorage به‌عنوان منبع حقیقت خوانده شود. برای عملیات بیرونیِ نیازمند retry، رخداد خروجی پایدار و تکرار امن طراحی می‌شود؛ افزودن ابزار صف پیش از نیاز قطعی الزامی نیست.

## تعریف اتمام قابلیت

- داستان و قواعد و خطاهای آن نهایی و ردیف پوشش تکمیل شده باشد.
- مدل و migration و API و مجوز و فرم مربوط با یکدیگر کار کنند.
- سناریوی مثبت، دسترسی غیرمجاز و شکست‌های مؤثر آن قابلیت آزموده شوند.
- اثر تغییر بر واحد پول، دادهٔ نامعلوم، نقش‌ها و مسیرهای مجاور روشن باشد.
- شواهد اجرایی با نسخهٔ کد و محیط ثبت شود؛ تأیید انسانیِ نیازمندی از موفقیت آزمون جدا بماند.
- مستند اجرا و پشتیبانی و تصمیم تعویق احتمالی به‌روز باشد.

## کنترل‌های این تحویل

استخراج ثابت آرشیوها، هش منابع، شمارش داده‌ها، بازتولید کاتالوگ و صحت ارجاعات مستندات بررسی می‌شوند. اجرا و screenshot نمونه، آزمون فرانت و بک‌اند، migration و اتصال AI هنوز انجام نشده‌اند. فایل `stage-status.json` همین تفاوت را نگه می‌دارد.


## خروجی گام راه‌اندازی رسمی

ابزار رسمی 1.4.1 در bootstrap جدا نصب و فایل‌های `.specify` و مهارت‌های Codex به پروژه منتقل شد؛ global قبلی دست‌نخورده است. constitution به نسخهٔ 1.0.0 رسیده و feature فعال `001-business-baseline` است. helperهای resolve-template، setup-plan، setup-tasks و check-prerequisites اجرا شده‌اند؛ تولید و بازبینی اسناد توسط عامل طبق مهارت‌ها انجام شده، نه با ادعای تولید خودکار بیزینس توسط CLI. extension hook ثبت نشده است.

Plan/research/data-model/contracts/tasks/test-plan/checklist موجودند اما draft هستند. نتیجهٔ analyze و گیت‌های باز در `docs/stage1/analysis.md` و `docs/stage1/report.md` ثبت می‌شود. امضای انسانی checklist و تست runtime با بررسی خودکار ساختار یکسان نیستند.
